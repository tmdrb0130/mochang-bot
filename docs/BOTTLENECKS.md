# 모창봇 병목 지도 — 대용량 트래픽 취약점

측정 2026-09-01 20:20–20:37 · 50 사용자 / 200 작업 / 496초
기록 `backend/.timing.jsonl` · 보고서 `scripts/timing_report.py`

50명이 실제 사용자처럼 서비스를 쓰는 상황을 재현해 측정했다. 한 건도 실패하지 않았지만,
사용자는 문항 하나를 받는 데 **3분 14초**를 기다렸다. 그중 모델이 일한 시간은 **24초**다.
나머지는 전부 줄이다.

각 항목의 *근거* 는 측정값이거나 코드 위치다. 추측으로 적은 항목은 없다.

---

## 1. 측정 요약

| 항목 | 값 | 비고 |
|---|---|---|
| 세션 성공 | 50 / 50 | 오류 0건 |
| 문항 1개 대기 | **3분 14초** | 그중 실행은 23.9초 |
| 최대 대기 건수 | **90** | 동시 실행은 12 고정 |
| 처리량 | **분당 24건** | 199건 ÷ 496초 |
| 전체 세션 | 5분 09초 | 최대 6분 49초 |
| 생성 분량 | 1,141자 | 목표 1900~2000 |

테스트 조건: 인테이크 1건 + 문항 3건 = 사용자당 4건, 총 200건.
50명이 90초에 걸쳐 순차 도착. 모두 중앙값 기준.

```
대기 vs 실행 (중앙값)

  문항 생성 (180건)   대기 2분 49초  |  실행 23.9초  →  합계 3분 14초
  인테이크  (50건)   대기   37.4초  |  실행 37.5초  →  합계 1분 15초
```

**대기가 길면 줄이 긴 것이고, 실행이 길면 모델이 느린 것이다.**
문항 생성은 대기가 실행의 7배 — 순수한 줄서기다.
인테이크는 실행 자체가 무겁다(검색 + 본문추출 + 모델 2회).

```
큐 추이 (5초 간격)

  20s  running=12  queued=0     ← 20초 만에 워커 포화
 149s  running=12  queued=85    ← 85명이 대기, 실행은 계속 12
 482s  running=10  queued=0     ← 8분 만에 해소

496초 동안 running 이 12에서 내려온 적이 없다
= 처리 능력이 아니라 대기가 병목
```

워커를 24로 올려도 총 처리량은 거의 같았다(45건 테스트).
대기가 실행으로 자리를 옮길 뿐, GPU 가 이미 포화 상태이기 때문이다.

## 2. 먼저 무너지는 순서

시스템은 세 층으로 되어 있고, 트래픽이 몰릴 때 **가장 아래층부터** 무너진다.
걱정하기 쉬운 GPU 는 오히려 가장 튼튼한 층이다.

### 1층 · 외부 웹 검색 — 가장 먼저 터짐 (수십 명 규모)

조사 단계가 DuckDuckGo 무료 검색과 외부 웹사이트 본문 요청에 의존한다.
사용자 1명이 9문항을 채우면 검색 36회, 페이지 요청 54회가 나간다.

| 동시 사용자 | 검색 | 외부 페이지 요청 |
|---|---|---|
| 50명 | 1,800회 | 2,700회 |
| 100명 | 3,600회 | 5,400회 |
| 500명 | 18,000회 | 27,000회 |

무료 검색은 이 트래픽을 허용하지 않는다.

### 2층 · SSH 터널 — 단일 장애점

사내 GPU 서버의 vLLM 에 `localhost:30800` 터널로 붙는다.
이 터널은 사람이 손으로 띄운 상태이고 서비스로 등록돼 있지 않다.
끊기면 조사·인테이크·생성이 전부 멈춘다.

### 3층 · 사내 GPU vLLM — 45명 동시 검증 완료

가장 튼튼하다. 45건 동시 요청에서 45/45 성공했고, 부하 중 작업 1건당 실행 시간이
21초에서 30초로 늘어나는 데 그쳤다. 다만 처리량 상한이 분당 24건이라
수백 명이 오면 대기가 시간 단위로 쌓인다.

## 3. 취약점 등록부

### V1. 프론트가 작업 큐를 쓰지 않는다 — 치명

- **근거**: `frontend/src/api.js:60` — `post("/generate", …)`. `/jobs/*` 호출 없음
- **증상**: 백엔드에 작업 큐 API 가 이미 있는데 프론트는 동기 엔드포인트만 부른다.
  사용자는 3분 넘게 HTTP 연결을 열어둔 채 빈 화면을 본다.
- **왜 위험**:
  - 50명이 문항 3개씩 요청하면 연결 150개가 수 분간 유지된다.
    nginx 는 `worker_processes 1` / `worker_connections 1024` 로 이 서버의 다섯 개 사이트가 그 1024를 나눠 쓴다.
  - 브라우저도 호스트당 동시 연결이 6개라 9문항을 한꺼번에 눌러도 6개씩 끊어 처리된다.
  - 네트워크가 한 번 끊기면 진행 중이던 작업을 되찾을 방법이 없다.
- **해결**: 프론트를 `/jobs/{kind}` 제출 + `/jobs/{id}` 폴링으로 전환.
  **백엔드는 이미 완성돼 있어 프론트만 고치면 된다.**
  V5·V6·V9 가 전부 여기에 묶여 있어 이것부터 푸는 것이 맞다.

### V2. 검색이 외부 무료 서비스에 의존한다 — 치명

- **근거**: `backend/requirements.txt` — `ddgs`, `trafilatura` / `backend/rag/research.py:164` `DDGSearch`
- **증상**: 검색을 DuckDuckGo 무료 API 로, 본문 추출을 외부 웹사이트 직접 요청으로 한다.
  `config.yaml` 주석에 **이미 캡차를 맞은 기록**이 남아 있다 —
  SearXNG 로 붙었을 때 봇으로 판정돼 살아남은 엔진이 Bing 하나뿐이었다.
- **왜 위험**: 지금 `ddgs` 가 버티는 건 브라우저 TLS 지문을 위장하기 때문이다.
  규모가 커지면 유지되지 않고, 약관상으로도 정당한 방법이 아니다.
  차단되면 참고자료 없이 생성하게 되는데, 그때 모델은 **통계와 출처를 지어낸다**
  (실측: 참고자료 없이 생성한 2건 모두 존재하지 않는 기관·보고서를 인용).
- **해결**: **자체 SearXNG 운영은 답이 아니다.** 메타서치라 자체 색인이 없고,
  결국 우리 서버가 남의 검색엔진을 긁게 되므로 서버 리소스와 무관하게 똑같이 차단된다.
  1. 아이디어당 1회만 조사하고 9문항이 나눠 쓰기 → 검색량 1/9
  2. 공공데이터(KOSIS·data.go.kr)를 미리 색인 → 요청 시 외부 호출 0회
  3. 남는 실시간 검색만 유료 API

### V3. 작업이 메모리에만 있다 — 치명

- **근거**: `backend/llm/jobs.py:75` — `self._jobs: OrderedDict` / `history_limit = 500`
- **증상**: 제출된 작업과 결과가 프로세스 메모리에만 있다. 서버를 재시작하면 전부 사라진다.
  완료 이력도 500건이 넘으면 오래된 것부터 삭제된다.
- **왜 위험**: 부하 테스트에서 8분에 200건이 처리됐다. 이 속도면 **20분이면 500건을 넘는다.**
  긴 대기 끝에 결과를 받으러 온 사용자가 `404 작업이 없습니다` 를 보게 된다.
  배포로 재시작할 때마다 대기 중이던 모든 사용자의 작업이 증발한다.
- **해결**: 결과를 디스크나 DB 에 저장하고 `history_limit` 을 시간 기준(예: 2시간)으로 바꾼다.
  재시작 시 대기 작업을 복구할지는 별도 판단이 필요하다.

### V4. 한 사람이 큐를 독점할 수 있다 — 치명

- **근거**: `backend/main.py` — 인증·레이트리밋 없음. `allow_origins=["*"]`
- **증상**: 사용자별 동시 작업 제한이 없다. 한 명이 문항 9개 × 스타일 3개 = 27건을
  한 번에 던질 수 있고, 워커가 12개뿐이라 그 사람 혼자 큐를 두 바퀴 채운다.
- **왜 위험**: 악의가 없어도 발생한다 — "전체 생성" 버튼을 누르면 그렇게 된다.
  게다가 인증이 없고 CORS 가 전면 개방이라 누구나 API 를 직접 호출할 수 있어,
  스크립트 하나로 서비스를 마비시킬 수 있다. 이 서버에는 이미 취약점 스캐너가 상시 돌아다닌다.
- **해결**: 세션(쿠키)당 동시 작업 수를 제한하고, 초과분은 큐가 아니라 즉시 거절한다.
  공개 전에는 `auth_basic` 이라도 걸어 둔다.

### V5. 대기 순번이 사용자에게 보이지 않는다 — 높음

- **근거**: 측정 — 대기 2분 49초 vs 실행 23.9초(7배) / `jobs.py` `snapshot()` 에 `position` 존재
- **증상**: 3분 넘게 아무 피드백이 없다. 큐는 `position`(앞에 몇 명)을 이미 계산하는데,
  프론트가 동기 API 를 써서(V1) 그 값을 받을 수 없다.
- **왜 위험**: 사용자는 고장 났다고 판단하고 새로고침한다. 그러면 진행 중이던 작업이 유실되고(V6)
  다시 요청해서 큐에 또 쌓인다. **부하가 스스로를 증폭시키는 악순환**이다.
- **해결**: V1 을 고치면 자동으로 풀린다. "앞에 32명 · 예상 4분" 을 보여주는 것만으로
  이탈과 재요청이 크게 줄어든다.

### V6. 새로고침하면 생성 중이던 작업이 사라진다 — 높음

- **근거**: `frontend/src/App.jsx:264` — status 가 `"loading"` 인 항목을 localStorage 에 저장하지 않음. `job_id` 도 미저장
- **증상**: 완성된 초안은 localStorage 에 남지만 **진행 중이던 것만 증발**한다.
  서버에서는 그 작업이 끝까지 돌아가 결과까지 만들고 버려진다.
- **해결**: `job_id` 를 함께 저장하고, 앱이 뜰 때 `/jobs/{id}` 로 다시 조회한다.
  V1 전환과 같이 하면 된다. 프론트 30줄 정도.

### V7. SSH 터널이 서비스로 등록돼 있지 않다 — 높음

- **근거**: `backend/config.yaml:69` — "base_url 이 SSH 터널이라 `ssh -L 30800:…` 이 켜져 있어야 한다"
- **왜 위험**: 2026-09-01 에 6개 서비스를 자동 복구 대상으로 만들었지만 **이 터널은 빠져 있다.**
  사람이 손으로 띄운 프로세스라, 같은 날 아침 25시간 다운을 만든 것과 같은 구조다.
- **해결**: `ssh -N -L 30800:localhost:30800` 를 NSSM 서비스로 등록해 자동 재시작시킨다.
  `ServerAliveInterval` 로 끊긴 터널을 스스로 감지하게 한다.

### V8. 분량 설정이 처리량을 직접 깎는다 — 높음

- **근거**: 측정 — 실행 시간은 출력 토큰 수에 비례. 목표 1900~2000자 / 실제 중앙 1,141자
- **증상**: 생성 시간을 지배하는 것은 출력 토큰 수다. 프롬프트를 줄여도 거의 안 변한다.
  지금은 목표가 2,000자인데 실제로는 1,141자밖에 안 나오면서도 24초를 쓴다.
- **왜 위험**: 역설적으로 **분량 목표를 낮추면 처리량이 오른다.**
  2,000자 → 1,200자면 처리량이 대략 1.6배가 되고 대기 시간은 그만큼 줄어든다.
  다만 신청서는 분량이 성의로 읽히는 면이 있어 사업 판단이 필요하다.
- **해결**: 문항별로 하한을 다르게 두는 방안을 검토한다. 입력이 빈약한 문항까지
  1,900자를 강제하면 모델이 같은 말을 반복해 채운다(실측: 6어절 구절이 6회 반복).

### V9. nginx 가 단일 워커로 다섯 사이트를 감당한다 — 중간

- **근거**: `nginx.conf:1` — `worker_processes 1` / `worker_connections 1024`
- **증상**: 연결 상한 1,024개를 bustartup.kr·모창봇·WeldLoop 등이 나눠 쓴다.
  V1 때문에 연결이 수 분씩 유지되면 이 한도에 훨씬 빨리 닿는다.
- **해결**: V1 을 고치면 연결이 초 단위로 짧아져 대부분 해소된다.
  그 뒤에도 부족하면 `worker_processes auto` 로 올린다.

### V10. 조사 캐시가 거의 재사용되지 않는다 — 중간

- **근거**: `backend/rag/pipeline.py:295` — `sha1(track|idea|question_id)`, 아이디어 문자열 완전 일치 / `.cache` 324개
- **증상**: "자취생 냉장고 앱" 과 "자취생을 위한 냉장고 관리 앱" 이 다른 키가 된다.
  캐시가 324개나 쌓였는데 신규 사용자는 사실상 매번 새로 검색한다.
- **해결**: 아이디어를 분야로 분류해 분야 단위로 캐시하고, TTL 만료분을 정리하는 작업을 둔다.
  V2 의 1번과 같은 작업이다.

## 4. 권장 순서

효과 대비 작업량과, 앞 단계가 뒤 단계를 풀어 주는 관계를 함께 고려한 순서다.

1. **프론트를 작업 큐로 전환** — V1 하나를 고치면 V5·V6·V9 가 함께 풀린다.
   백엔드는 이미 준비돼 있어 프론트 작업만 필요하다. **가장 먼저 할 일.**
2. **SSH 터널 서비스화** — 작업량이 가장 적고, 방치하면 언제든 전면 장애가 된다.
3. **사용자별 동시 작업 제한** — 공개 범위를 넓히기 전에 반드시 필요하다.
4. **조사 재사용(아이디어당 1회)** — 검색량이 1/9 로 줄어 1층 붕괴 시점을 크게 늦춘다. 외부 의존은 남는다.
5. **작업 결과를 디스크에 저장** — 재시작·이력 초과로 결과가 증발하는 문제를 없앤다.
6. **공공데이터 색인(RAG)** — 가장 큰 작업이지만 **외부 의존을 0으로 만드는 유일한 길**이다.
   신청서에 필요한 통계는 대부분 KOSIS·공공데이터포털이 정식 API 로 무료 제공한다.
   자료 품질도 오른다 — 실측에서 조사가 물어온 출처는 블로그였다(`restata`, `zachutip`, `1conomynews`).

## 5. 이 진단이 보지 못한 것

- **1층은 측정되지 않았다.** 외부 검색엔진 남용을 피하려고 아이디어를 10종으로
  제한해 조사가 캐시를 타게 했다. 실제로는 사람마다 아이디어가 달라 인테이크가 이 측정보다 느리다.
- **실제 사용자 경로가 아니다.** 부하 테스트는 `/jobs/*` 로 했지만
  실제 프론트는 동기 엔드포인트를 쓴다(V1). 실제 사용자는 연결 유지 문제를 추가로 겪는다.
- **GPU 서버는 공유 자원이다.** 다른 사람이 함께 쓰는 중이면 이 수치보다 느려진다.
  측정 시점에는 비어 있었다.
- **9문항 전체가 아니다.** 사용자당 3문항으로 측정했다.
  전체 흐름은 인테이크 1 + 문항 9 = 10건이라 대기가 2.5배가 된다.

## 6. 재측정 방법

```bash
# 서버측 기록 요약 (모델 호출 없음)
.venv/Scripts/python scripts/timing_report.py
.venv/Scripts/python scripts/timing_report.py --last 30    # 최근 30분
.venv/Scripts/python scripts/timing_report.py --tail       # 원본 20건
```

`backend/timing.py` 가 모든 HTTP 요청과 작업 완료를 `backend/.timing.jsonl` 에 남긴다.
작업 기록은 `queued_s`(대기) / `run_s`(실행) / `total_s`(합계)로 나뉘어 있어
느린 원인이 줄서기인지 모델인지 바로 구분된다.
