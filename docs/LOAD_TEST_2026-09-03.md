## 2. 회차별 진단과 바꾼 것 (판단 근거)

### 1차 → 병목은 GPU 가 아니라 "조사 워커 6"
- 30분 중 첫 15분 동안 vLLM 이 running 1~7 로 거의 놀았다. 조사용 LLM 호출 988건이 조사 큐(워커 6) 뒤에서 **중앙 2분 36초·최대 5분** 기다렸고 실행은 2.1초.
- 그 때문에 인테이크 1건이 서버에서 중앙 12분 55초 → nginx `proxy_read_timeout 600s` 를 넘겨 38/40 명이 504 → 프론트는 "조사 실패, 카드 없이 생성".
- 조사 워커 6 은 라마 70B 의 KV 캐시 한계(30 동시에 100%)에 맞춘 값. Qwen 은 KV 토큰이 5.3배(809k)라 그 제약이 없다(사전 프로브: 100 동시에 KV 81%, preemption 0).
- 부수: 요청 폭주 때 SSH 터널 연결이 openai 기본 연결 타임아웃 5초를 넘겨 `APITimeoutError` 3건 → 연결 타임아웃 30초로.
- **바꾼 것**: 조사 워커 6 → 24, 연결 타임아웃 5 → 30초.

### 2차 → 조사는 풀렸고, 남은 것은 GPU 총량
- 문항 조사 p50 115s → **17s**, 조사 LLM 큐 대기 2분 36초 → 9초. 전체 29분 → 22분.
- 인테이크는 여전히 서버 중앙 11분: 이제 대기가 아니라 **인테이크 안의 호출(검색어 1 + 페이지 추출 6 + 카드 1)이 생성 320건과 GPU 를 나눠 써** 호출당 1~1.5분, 카드 생성은 생성이 채운 본문 큐에서 최대 3분 47초 대기. 23/40 이 600s 초과.
- 계산: 40명 = LLM 호출 약 1,000건 ≈ GPU 20분치. 워커를 어떻게 나눠도 총 시간은 못 줄이고 **누가 먼저 받느냐**만 바뀐다.
- **바꾼 것 (3가지)**
  1. vLLM `--scheduling-policy priority` + 요청 `priority` (조사·인테이크 0 = 먼저, 본문 생성 100) — 카드·참고자료가 먼저 나오고, 생성은 순번이 보이는 큐가 대기를 흡수
  2. 인테이크·조사를 **작업 큐**로 (프론트 `api.js` 두 함수 → `runJob`, 인테이크 버튼에 "대기 중 — 앞에 N명"). 600s 절벽 제거. 백엔드는 이 작업들을 **조사 큐**(research_client.queue)에서 돌려 본문 워커를 점유하지 않게 하고, `/jobs/intake` 가 아이디어 조사를 빠뜨리던 버그(`_intake_full`)도 고침. 인테이크 카드 생성도 조사 클라이언트로(본문 큐 뒤에 안 서게 + 우선순위 '먼저')
  3. 인테이크·조사 응답 형태는 동기와 동일 → 프론트 표시 로직 변경 없음

### 3차 → 실패 0, 인테이크 40/40. 남은 것은 인테이크 실행 시간과 조사 큐 슬롯
- 인테이크 실패 0 (p50 244s). 전체 20분 18초, 사용자 p50 17분 58초(최소 15분 33초).
- 인테이크 **실행** 자체가 부하 때 p50 226s·최대 613s — 아이디어 조사(검색·페이지 수집·추출)가 GPU 를 생성과 나눠 쓰는 시간. 우선순위로 완화됐지만 GPU 총량 문제는 그대로.
- 인테이크 작업이 조사 큐(24) 슬롯을 4~10분씩 잡아, 실행 3초짜리 문항 조사가 큐에서 중앙 24초·p95 56초 대기. 인테이크도 16명이 최대 3분 42초 대기.
- 프론트가 "조사 8개 전부 끝 → 생성 8개" 순서라 서버에 **조사 파도 → 생성 파도**가 생김(조사 큐가 비는 순간 본문 큐 대기 71). 첫 초안은 전체 조사가 끝나야 나옴.
- **바꾼 것**
  1. 조사 워커 24 → 40 (GPU 배분은 vLLM 우선순위가 담당, KV 최고 44% 라 여유)
  2. 프론트 **문항별 파이프라인**: 조사가 끝난 문항부터 바로 생성 (조사 3 + 생성 3 동시 — 큐가 나뉘어 IP 당 제한도 큐별)
  3. 프론트 **카드 단계 선조사**: 카드가 뜨는 순간 문항 조사를 뒤에서 시작(캐시 키가 아이디어+문항이라 답과 무관하게 재사용). 같은 문항 중복 조사 방지(진행 중 Promise 공유)
  4. 부하 스크립트도 같은 파이프라인 + 카드 답 시간 45초 흉내 + "첫 초안 도착 시간" 지표

### 4차 → 조사는 사라졌지만 총 시간은 그대로 — GPU 총량이 상한임을 확인
- 문항 조사가 카드 답하는 동안 끝나 사용자 체감 p50 **2.6초**(3차 35초). 조사 큐 대기 0, 인테이크 큐 대기 0(워커 40 이라 40명이 한 번에 실행).
- 그런데 전체는 20분 59초(카드 답 45초 포함, 빼면 3차와 ±1분) — **조사를 앞당긴 만큼 생성이 더 일찍 몰려**(본문 큐 대기 p50 127s → 157s) 총합은 같다. GPU 가 처음부터 끝까지 바쁘면 그 이상은 못 줄인다는 예측 그대로.
- 인테이크 실행 p50 226s → 401s 로 늘었다: 24명이 아니라 40명이 동시에 인테이크를 돌리니 서로 GPU 를 나눠 쓴다. 대신 p95 는 777s → 588s 로 꼬리가 짧아졌다(줄 서던 16명이 사라짐).
  → 조사 워커 24 와 40 은 "중앙값 vs 꼬리" 트레이드오프이고 총량은 같다. **아무도 10분 넘게 기다리지 않는 40 을 택한다.**
- vLLM 처리량 실측(생성 구간 20초 샘플): 생성 216 tok/s + prefill 3,700 tok/s. 프롬프트 4천 토큰짜리 호출(본문·폴리시·이어쓰기·추출)이 많아 **prefill 이 GPU 시간의 큰 몫**.
- 실패 0, preemption 0, KV 최고 37%. 안정성 문제는 없다.
