# 창업교육 MVP 도달 프로세스 — 신청서 문항 매핑과 프롬프트 개선 기준

## 1. 프로세스 (원본)

① 문제 발견 → ② 고객 정의 → ③ 문제 검증 → ④ 해결책 설계 → ⑤ 비즈니스 모델 → ⑥ MVP 기획 → ⑦ MVP 제작 → ⑧ 고객 검증

| 단계 | 핵심 질문 | 교육 내용 | 결과물 |
|---|---|---|---|
| 1. 문제 발견 | 어떤 문제가 있는가? | 생활·산업·지역사회 문제 탐색 | 문제 리스트 |
| 2. 고객 정의 | 누가 이 문제를 겪는가? | 고객 세분화, 페르소나 | 핵심 고객 |
| 3. 문제 검증 | 정말 불편한 문제인가? | 인터뷰, 설문, 관찰 | 검증된 문제 |
| 4. 해결책 설계 | 어떻게 해결할 것인가? | 아이디어 발상, 경쟁제품 분석 | 해결 아이디어 |
| 5. 비즈니스 모델 | 어떻게 가치를 만들고 수익을 낼 것인가? | 가치제안, 고객·수익모델 | BM 캔버스 |
| 6. MVP 기획 | 가장 최소한으로 무엇을 만들 것인가? | 핵심 기능 선정, 사용자 시나리오 | MVP 설계서 |
| 7. MVP 제작 | 실제로 작동하는가? | AI·노코드·코딩·프로토타이핑 | 작동 가능한 MVP |
| 8. 고객 검증 | 고객이 실제로 사용하는가? | 사용성 테스트, 피드백, 개선 | 검증 결과 및 개선안 |

원본 표기 메모: 상단 흐름은 "④ 해결책 **설계**", 표는 "4. 해결책 **도출**" — 이 문서와 프롬프트는 **"해결책 설계"** 로 통일한다.
8단계 교육 내용은 원본 이미지에서 "용성 테스트"로 잘려 보였으나 문맥상 **"사용성 테스트"** 로 적는다 (원본 확인 시 다르면 수정).

## 2. 도전신청서 문항 ↔ 단계 매핑

| 문항 | 다루는 단계 | 그 단계의 언어·결과물이 글에 드러나야 하는 것 |
|---|---|---|
| Q1 한 줄 소개 | ②④(⑤ 가치제안) | 핵심 고객 + 해결 아이디어를 한 문장에. 가치제안 문장 |
| Q2 배경 이야기 | ①③ | 문제를 **발견한 장면**과 **검증한 방법**(직접 겪음/인터뷰/설문/관찰 — 인테이크 `evidence`). 검증된 문제 |
| Q3-1 차별점·해결 문제 | ④(③) | 경쟁제품·기존 우회책 분석(인테이크 `alternative`) → 해결책 설계. "왜 우리 방식이 다른가" |
| Q3-2 수익 창출 | ⑤ | 가치제안·고객·수익모델 — BM 캔버스 항목 언어(누가, 무엇에, 어떤 방식으로 돈을 내나) |
| Q4-1 사업화 계획 | ⑥→⑦→⑧ | **MVP 기획(핵심 기능 선정·사용자 시나리오) → MVP 제작(AI·노코드 등 방법) → 고객 검증(사용성 테스트·피드백·개선)** 순서의 단계 계획 |
| Q4-2 멘토 도움 | ①~⑧ 중 막히는 단계 | "어느 단계에서 무엇이 부족한가"로 요청을 특정 |
| Q8 본인 역량 | ①~⑧ 중 스스로 할 수 있는 단계 | 경험·기술을 단계에 붙여 증명 (Q4-2 와 겹치지 않게) |
| Q10 자랑 | ⑤ 가치제안 | 대중 언어로 된 가치제안 |
| Q7-1 이종창업 | ① | 기존 사업과 **문제 자체가 다름** |
| 인테이크 슬롯 | customer②, problem①, evidence③, alternative·solution④, revenue⑤, first_step⑥⑦, capability⑦, mentoring(막히는 단계) | |

## 3. 프롬프트 개선 기준 (세션3 작업 16)

1. **공통 프레임 1개 추가** — `backend/prompts/process.md`(신규, `tests/test_prompts.py` 등록). 8단계를 8줄로: 단계명·핵심 질문·결과물.
   `assemble.build_prompts` 가 system 에 한 번 넣는다. 인테이크(`intake.md`)에도 같은 블록.
2. **문항 md 마다 `[프로세스 위치]` 절** — 위 매핑표의 단계와 "이 글에 드러나야 하는 결과물"을 2~3줄로. 기존 [문항 의도]·심사 축(P/S/BM/T)은 유지 — 심사 프레임(심사위원 관점)과 프로세스(지원자가 밟은 단계)를 **둘 다** 쓴다.
3. **Q4-1 은 구조를 바꾼다** — "⑥ MVP 기획 → ⑦ 제작 → ⑧ 고객 검증" 이 글의 뼈대가 되게. 인테이크 `first_step` 이 ⑥⑦의 첫 행동이 된다.
4. **Q2 는 ③ 문제 검증을 반드시 쓴다** — `evidence` 가 "없음"이면 "검증 계획"(누구를 어떻게 인터뷰/관찰할지)으로 쓰고, 검증한 것처럼 지어내지 않는다.
5. **어휘** — 페르소나·가치제안·BM 캔버스·MVP·사용성 테스트 같은 프로세스 용어는 **한 문항에 1~2회**만. 교재 베끼기처럼 보이면 감점.
6. **안 바꾸는 것** — 글자수·문체 규칙(`short_question.md`, `styles/`), 참고자료 인용 규칙(`sections.md`), 출력 형식. 작업 15(Q1 문체)와 충돌하지 않게 Q1 은 15 이후에.
7. **검증** — 실호출: 같은 아이디어(인테이크 포함) 1인분 개선 전 1회·후 1회 = 라마 약 20회. 문항별로 "단계 언어가 들어갔는가 / 지어낸 검증이 없는가 / 글자수 유지" 를 표로 로그에.
   pytest(`test_prompts.py` 포함) 통과.

## 4. ⚠️ 프롬프트 편집은 운영에 즉시 반영된다

`assemble._read` 는 **요청마다 md 를 다시 읽고** 캐시가 없다. 운영 `mochang-api` 는 이 작업 폴더(`C:\Users\bon505\Desktop\mochang-bot`)에서 돈다.
→ `backend/prompts/*.md` 를 저장하는 순간 공개 서비스의 다음 요청부터 그 프롬프트를 쓴다. 재시작 불필요 = **되돌리기도 파일 복원만으로 즉시**.

작업 중 미완성 프롬프트가 사용자에게 나가지 않도록 세션3 은 **git worktree** 에서 작업한다:
```
git worktree add ../mochang-prompts llama-switch-and-diagnostics
```
worktree 에서 md 를 고치고 실호출 검증(`.venv` 는 공유, 경로만 worktree)을 마친 뒤 커밋 → 본 작업 폴더에서 `git pull`/merge 하면 그 시점에 운영 반영.
문제가 보이면 `git checkout prompts-before-mvp-2026-09-02 -- backend/prompts` 로 즉시 원복.
