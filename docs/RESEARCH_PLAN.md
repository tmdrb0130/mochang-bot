# 자료조사 파이프라인 개편 계획

> 2026-09-02 사용자 지시서. 세션1이 코드로 수치 검증 완료 — 아래 실측은 전부 사실 확인됨.
> WORKBOARD 작업 5(조사 재사용)·7(소스 다양화)·8(API 추가)을 이 계획의 단계로 **흡수**한다.
> 벡터DB 축적(`docs/RAG_PLAN.md`)은 별도 층 — 관계는 맨 아래 참조.

## 배경 (검증된 실측)

- 조사 1회 = 외부 요청 20건: DDG 8회(`max_queries: 4` × text+news 각 1회) + 페이지 fetch 12회
  (`pipeline.py:141` 의 `max_pages_to_extract * 2` = 12개 받아 6개만 사용 — 절반 낭비)
- 사용자 1명 = 조사 최대 10회(인테이크 1 + 문항 9) ≈ 200요청. 아이디어 수정마다 전체 재조사
  (캐시 키가 `sha1(track|idea|question_id)` 완전 일치 — `pipeline.py:295`)
- 전부 서버 단일 IP에서 DDG(비공식)로 나감 → 수백 명 규모에서 캡차·차단 확정 (BOTTLENECKS V2)

## 목표

- DDG 를 "최후 폴백"으로 강등, 근거 유형별 정식 무료 API 로 분산
- 전 소스가 각자 일일 한도의 10% 미만
- **완료 조건**: 1인 시나리오(인테이크+9문항+아이디어 1회 수정) 실측 → 외부 요청 총 40건 이하,
  그중 ddgs 5건 이하. 소스별 호출 카운터를 로그로 남겨 한도 대비 사용률 확인 가능할 것.

## 단계 (효과 큰 순, 단계마다 커밋)

### 0단계 — 사전 분석 (구현 전 필수)
9개 문항별 실제 생성 검색어를 덤프해 중복도 분석 → 2단계 설계 확정.
(모델 호출 필요 — 라마라 한도 부담 없음. 결과는 이 문서에 추가 기록.)

### 1단계 — 즉시 수정 (키 불필요, 바로 가능)
- `pipeline.py:141` 의 `* 2` 제거 → fetch 12 → 6 (실패 대비 필요하면 8까지만)
- `research.py:179` 의 `d.news()` 호출 제거 — 단 뉴스 기능 자체는 삭제하지 말고
  3단계에서 네이버 뉴스 API 로 이관 ("산업 동향" 근거는 유지 가치 있음)
- 효과: DDG 호출 절반, fetch 절반. 두 줄 수정.

### 2단계 — 아이디어당 1회 조사 (구 작업 5)
문항 9개가 조사 결과를 공유 (조사 10회 → 1~2회, 200요청 → 20~40).
0단계 분석으로 "공통 조사 1회 + 문항별 추가 검색 최소화" 형태 설계.

### 3단계 — 근거 유형별 API 라우팅 (핵심, 구 작업 7·8)

질의를 유형 분류해 라우팅. 정형 데이터는 검색+fetch 자체가 사라진다 (JSON 직조회).

|---|---|---|---|
| 시장규모·산업·인구·고용 통계 | KOSIS OpenAPI | data.go.kr 부처 통계 | JSON 직조회, fetch 불필요 |
| 상권·업종별 사업체 수 | 소상공인시장진흥공단 상권정보 API | KOSIS | 좌표·업종코드 기반 |

키 없이도 어댑터+mock 테스트까지 선작업 가능.

### 4단계 — 캐시 개편
- 키 정규화: 공백·조사·어미 제거 후 해시 ("냉장고 앱" ↔ "냉장고 관리 앱" 흡수)
- 정형 소스(KOSIS/상권)는 아이디어 문장이 아니라 **업종분류코드·통계표ID** 를 키로
  → 아이디어를 고쳐도 같은 업종이면 적중
- 뉴스류는 검색어+날짜(일 단위) 키로 24h 캐시
- 기존 7일 디스크 캐시는 유지

### 5단계 — 동시성·장애 대응
- 소스별 토큰버킷 레이트리미터 (네이버 초당 5~10부터, config 설정값으로)
- 소스별 서킷브레이커: 연속 N회 실패(429/캡차/타임아웃) 시 일정 시간 제외하고 폴백
- 요청 대기열 + 프론트 "자료 조사 중" 진행 표시로 burst 흡수 (프론트 몫은 세션2와 조율)

## API 한도·제약 (반드시 준수)

- **네이버 검색 API — NAVER API HUB 기준 (2026-06-25 이관, 2026-09-02 확인)**:
  - 신청: developers.naver.com **아님**(신규 신청 종료). 네이버클라우드플랫폼 콘솔 > Application Services >
    NAVER API HUB > Application 등록 > 검색 API. 구 키는 2027-06-30 까지만.
  - 엔드포인트: `https://naverapihub.apigw.ntruss.com/search/v1/{news|blog|webkr|cafearticle|…}`
    (구 `openapi.naver.com/v1/search/{kind}.json` — 도메인만 바꾸면 안 됨, 경로도 다름).
    파라미터는 동일: query, display(1~100), start(1~1000), sort(sim|date).
  - 헤더: `X-NCP-APIGW-API-KEY-ID`(Client ID) / `X-NCP-APIGW-API-KEY`(Client Secret) — 구 `X-Naver-Client-*` 아님.
  - 한도: 검색 통합 **월 775,000건**, 키당 **50 RPS**, 초과 시 429. 콘솔에서 일/월 한도와 50/80/100% 알림 설정.
  - 오류: HTTP 상태 먼저 보고, 본문은 `{"errorCode","errorMessage"}`(API) 와
    `{"error":{"errorCode","message"}}`(게이트웨이) 두 형태 모두 파싱.
  - **전문자료(doc)·책·쇼핑은 2026-07-31 종료** — `doc` kind 는 코드에서 제거. 구 openapi 예제 코드 참고 금지.
  - 초과 대응은 다계정이 아니라 콘솔 한도 상향 신청으로.
- **data.go.kr**: 개발계정 1,000회/일 → **서비스 오픈 전 운영계정 전환 신청 필수**(최대 10만/일).
  1인 1키 원칙 — 키 복수 발급 우회 금지.

     - KCI 어댑터는 `no_fetch` — API 가 주는 제목·저자·학술지·연도·초록·링크만 쓴다. 원문 PDF 는 어떤 경로로도 받지 않는다.

       facts 의 quote 는 그 범위 안에서 출처와 함께 인용.
     - 기존 캐시의 KCI 항목 107건(12:1x 실측)은 전부 논문 상세 페이지(`kciportal/ci`·`landing`) 스니펫이고 PDF·본문 전체가 없어 **삭제하지 않는다** — 7일 후 자동 만료.

  3. **왜곡 금지** — KCI 항목은 제목·저자·연도·학술지를 있는 그대로. 모델이 요약·수치화해 "논문에 따르면 N%" 로 만들지 않는다

  6. 목적 외 사용 금지 — 산업 분야별 학술 근거 조회 외 용도(예: 대량 크롤링, 별도 데이터셋)로 쓰지 않는다.
- API 키는 전부 `.env` — 코드·커밋 포함 절대 금지.

## RAG_PLAN(벡터DB) 과의 관계

- 이 계획 = **소스에서 가져오는 방법** 개편. RAG_PLAN = **가져온 것을 쌓아 재사용하는 층**.
- 벡터DB 색인 대상은 비정형 본문(뉴스·웹문서·보고서). 정형 API(KOSIS 등) 결과는 fetch 가 없어
  4단계의 코드 기반 캐시가 담당 — 벡터화 불필요.
- 구현 순서: 이 계획 1~3단계 → RAG 색인층 → 4~5단계와 RAG 조회층은 병행 가능.
