### 작업 13 상세 — GPU 상한 실측 확대 (세션3 + 사용자)

- 목적: "맥스로 하면 몇 개까지 병렬로 처리되나, 그때 GPU 를 얼마나 먹나" — 작업 10 의 45 는 한계가 아니었다
  (KV 캐시 7%, waiting 0, preemption 0). 한계가 보일 때까지 올려서 잰다.
- 방법 (`scripts/gpu_probe.py`, 코드 수정은 필요한 만큼만):
  1. `--levels 60,80,100,150` — **실사용 길이 프롬프트**로 (참고자료 facts 8건 붙인 문항 생성 프롬프트, `max_tokens 1200`).
     작업 10 은 짧은 프롬프트라 KV 를 실제보다 적게 썼다.
  2. 단계마다 vLLM `/metrics`: `num_requests_running`·`num_requests_waiting`·`kv_cache_usage_perc`·preemption 을 1초 샘플링.
     **`running` 이 동시성보다 작게 머무는 지점 = vLLM `--max-num-seqs` 상한** → 그 위는 GPU 서버 설정을 바꿔야 함(리포 밖, 사용자).
  3. 사용자: 같은 시간에 PuTTY 로 GPU 서버에서 `nvidia-smi --query-gpu=utilization.gpu,memory.used,memory.total --format=csv -l 1`
     → 단계별 최대치를 세션3에 전달 (GPU 사용률·메모리).
  4. 판정: KV 캐시 90% 근접 / p95 가 직전 단계보다 1.5배 이상 꺾임 / preemption>0 / 실패 발생 — 넷 중 하나가 걸리는
     **직전 단계가 안전 상한**. 본문:조사 = 4:1 로 나눠 `max_workers`·`research.llm.max_workers` 반영 → 재시작(사용자).
- 결과 표는 작업 10 형식 그대로 세션3 로그에. 요약(안전 상한·GPU 사용률)은 세션1이 PROGRESS 로 이관.
- ⚠️ 공유 GPU 라 실행 시점은 사용자 승인. 라마 실호출 ~400회(측정용, 한도 무관).

### 작업 10 상세 — GPU 한계 측정과 워커 상향 (세션3 + 사용자)

**현황 근거** (어제 측정, PROGRESS·BOTTLENECKS):
- 백엔드 큐 `max_workers: 12` (본문) + 4 (조사) — 부하테스트 내내 `running=12` 고정, 대기 최대 90건.
  **대기(2분49초)가 실행(24초)의 7배 — 병목은 GPU 가 아니라 우리 쪽 워커 수.**
- vLLM 직접 45 동시 호출은 45/45 성공, 73초 — GPU 쪽에 여유가 있다는 뜻.

**측정 (코드 수정 없음, 세션3):**
1. vLLM `/metrics` 를 터널(30800) 경유로 조회 — `vllm:num_requests_running`,
   `vllm:num_requests_waiting`, KV 캐시 사용률이 핵심 — **이 vLLM 의 실제 지표명은 `kv_cache_usage_perc`** (9/2 스모크로 확인).
   SSH 필요 없음 — 백엔드가 쓰는 같은 포트다.
2. `scripts/load_test.py` 로 동시성을 **단계적으로** 12 → 20 → 30 → 45 올리며
   문항당 p50/p95 실행 시간과 `gpu_cache_usage_perc` 를 기록.
   **KV 캐시가 90% 근처로 가거나 p95 가 꺾이는 지점의 한 단계 아래가 안전 상한.**
3. `nvidia-smi` (GPU 사용률·메모리)는 사용자가 PuTTY 로 원격 서버에서 확인해 값만 전달.

**적용:** `backend/config.yaml` `max_workers` 를 측정된 안전 상한으로 (한 줄).
되돌리기도 한 줄이라 위험 낮음. 조사 워커(4)도 같은 방식으로.

**⚠️ 조율:** 부하 테스트는 공유 GPU 서버에 실부하를 건다 — **실행 시점은 사용자 승인 후**
(한가한 시간대 권장). GPU 서버 자체 설정(vLLM 재기동, `--max-num-seqs` 등)은 이 리포 밖 —
필요해지면 사용자가 직접.
